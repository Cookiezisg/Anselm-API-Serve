## A. Financial correctness

| id | category | one-sentence statement | why | concrete failure if broken | how to test |
|---|---|---|---|---|---|
| GW-INV-01 | financial | The three guardrails (monthly count `usage.count < MonthlyQuota`, install-day tokens `usage.tokens + est <= InstallDailyTokenCap`, global-day budget `budget.tokens_used + est <= GlobalDailyBudget`) are pessimistically pre-reserved in ONE `BeginTx` on the write pool (`Reserve`), each as a conditional `UPDATE ... WHERE ...`; any `RowsAffected()==0` returns the matching `APIError` and rolls back the whole tx (deferred `tx.Rollback` until `committed=true`). | Atomic 3-in-1 reserve under the serialized single-writer pool is the only way to prevent oversell / wallet drain under concurrency without post-hoc accumulation. | Concurrent spikes oversell quota/budget; a wallet can be drained past `GlobalDailyBudget`. | `TestConcurrent*NoOversell`, `TestBudgetExhausted`, `TestHandlerConcurrencyBoundedAndConsistent` (quota/proxy): N goroutines on one install → total debit == min(N, quota); budget never exceeds limit. |
| GW-INV-02 | financial | A pre-output failure (retry exhausted, breaker open, all keys down, marshal error, queue timeout, client cancel while queued) rolls back ALL THREE reservations plus the day request-count `requests-1` and (if enabled) the daily sublimit `count-1` via `quota.Rollback`, driven by the single REL-5 defense point `outputStarted bool` + `defer{ if !outputStarted { h.rollback } }` in `forward`. | Missing a budget rollback lets an abused/failed request virtually occupy the day's wallet forever; partial rollback corrupts conservation. | Failed requests silently consume the daily budget; `tokens_used` drifts up with no served output. | `TestPreOutputFailureRollsBackBudget`, `TestUpstreamHeaderTimeoutRollsBack`, `TestRollbackConservation` (proxy/quota): upstream error/timeout/breaker → budget back to 0 + month count reverted; `Rollback` conserves all three. |
| GW-INV-03 | financial | Billing is counted EXACTLY ONCE at first byte: streaming arms `outputStarted=true` only after `br.Peek(1)` succeeds; non-stream after a 2xx header; output begun → count is KEPT even on mid-stream disconnect and the request is never retried. | The "算一次" boundary must be upstream's first produced byte, else either every transient retry double-bills or deliberate mid-stream disconnect dodges billing. | Either double-billing on retried streams, or free usage via deliberate client disconnect after first byte. | `TestStreamingPassthroughAndSettle`, `TestHandlerClientDisconnectKeepsCount`, `TestUpstream429MapsBusy` (proxy): first-byte gates 200; post-first-byte disconnect keeps count + full `est` settle. |
| GW-INV-04 | financial | Settle, Rollback, and ReconcileOrphans are mutually-exclusive idempotent via the `ledger.settled IS NULL` guard: each first does `UPDATE ledger SET settled=? | GW-INV-05 | financial | The `Period{Month,Day}` is snapshotted ONCE at request entry (`SnapshotPeriod(h.now())` in `h.cfg.Load().Location`) and the SAME `p` is threaded through Reserve/Settle/Rollback; it is NEVER recomputed in settle/rollback. | A zero-crossing midnight concurrent settle/rollback recomputing the period would apply to a different `period_day`/`period_month` row, breaking conservation. | Cross-midnight requests settle against the wrong day row; budget for two days corrupted. | `TestPeriodSnapshotReuse` (quota): reserve/settle/rollback use the identical passed-in `Period`, never recompute. |
| GW-INV-06 | financial | A crash that leaves a `settled IS NULL` ledger row can only ever OVER-count (conservative): on stream success usage is topped-down via Settle, but a crash before settle leaves the reservation held until `ReconcileOrphans(older=10m)` refunds full `reserved` on `budget` + install-day `usage` and marks `settled=reserved`; the +1 month count is intentionally kept. | Crash-only-overcount is the safe direction; under-counting would let abuse slip free, but virtual occupancy must eventually release so the day budget is not chronically pinned. | Without reconcile, crash-left reservations chronically occupy the day budget; or a non-conservative crash path under-bills. | Orphan reconciliation test in quota (`ReconcileOrphans` refunds settled-NULL rows older than cutoff); startup + 5-min ticker sweep in `main.runReconciler`. |

## C. Reliability

| id | category | one-sentence statement | why | concrete failure if broken | how to test |
|---|---|---|---|---|---|
| GW-INV-21 | reliability | Total gateway→upstream in-flight is `<= N_GLOBAL_CONCURRENCY` and is NEVER amplified: `sem := make(chan struct{}, c.NGlobalConcurrency)` is a fixed-capacity account-level hard cap, deliberately NOT resized on hot-reload (restart-effective), and multi-key failover only changes WHICH key is used, never adds an in-flight slot. | The account-level concurrency ceiling protects the upstream account + fixed bandwidth; key switching or queueing must never exceed it. | Upstream account-level concurrency cap exceeded; bandwidth saturation; upstream throttles/bans the account. | `TestHandlerConcurrencyBoundedAndConsistent` (proxy), REL-3 maxInFlight ≤ N_global test: in-flight never exceeds N_global even across key failover. |
| GW-INV-22 | reliability | The process-wide breaker EXCLUDES client-cancel and 429 from its failure count: it trips on `ConsecutiveFailures >= 5` OR (`Requests >= 10` AND failure-rate `> 0.5`), counts only genuine upstream faults (`breakerFault=true`: 5xx/timeout/connect via `errUpstreamFault`), records exactly ONE failure per attempt-set, and a queued-then-client-canceled request returns `499 CLIENT_CANCELED` with full rollback and is NOT charged busy / NOT a breaker fault. | Counting client cancels or 429 would trip the breaker on healthy upstreams and self-inflict an outage. | Breaker opens on client behavior / upstream busy and sheds all traffic on a healthy upstream. | `TestBreakerOpenFires`, `TestClientCancelWhileQueued`, `TestUpstream429MapsBusy` (proxy/alert): cancel→499 no busy/no breaker; 429 not counted. |
| GW-INV-23 | reliability | Upstream 429 is its OWN class `UPSTREAM_BUSY` (429): it is NOT retried, NOT a breaker fault, and NOT misclassified as a pre-output error; in the per-key transport a plain 429 does not trip the key (only a 429 with `Retry-After > 5s` sets a per-key cooldown). | 429 is a backpressure signal, not a fault; retrying/breaking on it amplifies the overload and corrupts billing classification. | Retry storms on upstream 429; breaker opens; 429 mistaken for a fault and double-handled. | `TestUpstream429MapsBusy` (proxy): 429 → `UPSTREAM_BUSY`, no retry, no breaker count, full rollback. |
| GW-INV-24 | reliability | Shutdown closes the DB LAST (REL-4): every detached settle/rollback + reconciler + prober + diskguard + metrics loop is tracked by the shared `bgWG`, and shutdown order is strictly ① `scanCancel()` (stop loops) ② `srv.Shutdown` + `adminSrv.Shutdown` ③ `waitWithTimeout(&bgWG, 30s)` ④ `st.Close()`; `st.Close` is deliberately never `defer`'d. | Closing the DB while a detached settle/rollback is writing corrupts accounting (a reservation never settles). | DB closed mid-settle → corrupted ledger / permanently unsettled reservations. | `TestCloseIdempotent` (store) + `waitWithTimeout` two-branch test (cmd/server): drain→true before Close; stuck→timeout false, no deadlock; bgWG drains before `st.Close`. |
| GW-INV-25 | reliability | Streaming uses a ROLLING per-frame write deadline, never a global `http.Server.WriteTimeout`: `streamThrough` calls `rc.SetWriteDeadline(h.now().Add(30*time.Second))` on each frame, and the `http.Server` is constructed with NO `WriteTimeout` (only `ReadHeaderTimeout`/`ReadTimeout`/`IdleTimeout`). | A global write timeout would truncate long LLM streams mid-response; the connect→header phase is bounded separately. | Long valid streams truncated at the global write timeout; clients lose responses. | `TestStreamingPassthroughAndSettle` (proxy): full stream relays to `[DONE]`, each frame rolls the deadline, never truncated. |
| GW-INV-26 | reliability | Retry is bounded to the connect→first-byte window ONLY (REL-1): `defaultRetryPolicy{maxAttempts:3, base:200ms, cap:3s}` with exponential backoff + full jitter (`rand.Int64N(d+1)`), retries only transient faults (connect fail / TLS reset / 502·503·504, NOT 429), reuses the SAME reservation (est unchanged) and only rebuilds the upstream request, and NEVER retries after `outputStarted=true`. | Retrying after output begins double-bills and double-produces; retrying 429 amplifies overload. | Produced output retried → duplicate billing + duplicate response bytes to the client. | `TestPreOutputFailureRollsBackBudget` (≤3 503s→200 billed once), `TestHandlerClientDisconnectKeepsCount` (post-output no retry) (proxy). |
| GW-INV-27 | reliability | The connect→header phase is bounded by `UPSTREAM_HEADER_TIMEOUT_SEC` (default 60s) via a per-attempt first-byte timer (`time.AfterFunc` → `cancelUp`) read LIVE from `cfg.Load()` each attempt; the timer is STOPPED the instant output begins (Peek ok / 2xx headers) so the streaming body is never bounded by it. | An upstream that accepts the connection but never replies would otherwise pin an `N_global` slot and virtually occupy budget indefinitely. | A stalled upstream pins concurrency slots + virtually occupies budget forever. | First-byte-timeout proxy tests: stalled header → retryable timeout/rollback; started stream not cancelled by the timer. |
| GW-INV-28 | reliability | REL-7 overload backpressure is bounded WAIT, not binary reject, and never amplifies: `acquireSlot` fast-paths a free slot, else waits up to `QueueWait` (`QUEUE_WAIT_MS` default 1500, `0`=binary reject) selecting on `sem<-{}` / `timer.C` / `ctx.Done()`; timeout → `429 UPSTREAM_BUSY` + rollback, client-cancel → give up WITHOUT taking a slot; sem capacity stays `= N_global`. | Absorbing spikes via a short queue improves availability without ever raising the account-level concurrency ceiling. | Either harsh spike rejection, or queue-induced concurrency amplification beyond N_global. | `TestQueueWaitAbsorbsSpike`, `TestQueueWaitTimeoutBusy`, `TestClientCancelWhileQueued` (proxy, -race): spike absorbed; timeout→429+rollback; cancel→no slot; N_global not amplified. |
| GW-INV-29 | reliability | REL-6 low-disk read-only degradation sheds BEFORE any reservation: diskguard probes the data disk every 30s, flips `degraded` atomically when free `< DISK_MIN_MB` (default 500) OR `< DISK_MIN_PERCENT` (default 5), the proxy checks `h.degraded()` pre-reserve and returns `503 DISK_LOW`, the flag is primed synchronously (`dg.Check()`) before serving, probe failure is FAIL-OPEN, and recovery auto-clears; WAL growth is bounded by `wal_autocheckpoint` (4000 pages). | Letting SQLite silently fail a mid-write on a full disk corrupts the conservative accounting; pre-reserve shed avoids it. | Disk-full mid-write corrupts the ledger/budget; or a probe blip wedges the box read-only. | `TestDiskLowSheds` (proxy), `TestAbsoluteFloorFlipAndRecover`/`TestPercentFloor`/`TestProbeErrorFailOpen`/`TestSynchronousPrimeFromOptimisticDefault` (diskguard). |
| GW-INV-30 | reliability | Multi-key failover (REL-3) isolates per-key health WITHOUT amplifying concurrency: `redactingTransport` holds `[]*keyState` each with its own gobreaker + cooldown; 401/403 → 10-min cooldown + key switch, persistent 5xx → per-key breaker, plain 429 → not a key fault; `pickKey` round-robins healthy keys; key events audit by `key_index` only; single-key config behavior is unchanged. | A single dead key must not trip the whole upstream or leak; load must spread across healthy keys without adding in-flight slots. | One bad key takes the whole upstream offline, or key rotation amplifies in-flight concurrency. | `TestRedline_KeyNeverInLogs` + REL-3 failover tests: key0 401→cooldown→key1 success; maxInFlight ≤ N_global; single-key unchanged. |

## Notes for the rewrite

- **Wire-code contract** (must be preserved verbatim — `internal/httpx/errors.go`): `INVALID_TOKEN`(401), `ACCOUNT_BANNED`(403), `RATE_LIMITED`(429), `QUOTA_EXHAUSTED`(429), `UPSTREAM_BUSY`(429), `BUDGET_EXHAUSTED`(402), `BAD_REQUEST`(400), `UPSTREAM_ERROR`(502), `UPSTREAM_TIMEOUT`(504), `INSTALL_RATE_LIMITED`(429), `INSTALL_CAP_REACHED`(429), `INSTALL_FP_LIMITED`(429), `INSTALL_POW_REQUIRED`(403), `INSTALL_POW_INVALID`(403), `DISK_LOW`(503), plus the internal `CLIENT_CANCELED`(499) audit code. Envelope is `{"error":{"code","message"}}`; a non-APIError normalizes to `500 INTERNAL`.
- **Schema is forward-only** (OPS-1): tables `installs`, `usage`, `budget`, `ledger`(+`idx_ledger_open`), `install_ip_rate`, `install_global_rate`, `install_fp_rate`, `settings`. The `settled` column is nullable INTEGER and is the idempotency pivot for GW-INV-04/06. `installs.fingerprint` stores plaintext for MVP observability only (no UNIQUE, never a merge key); the durable Sybil key is `install_fp_rate.fp_sha256`.
- **Middleware chain order** (`internal/server/server.go`, single source of truth shared by main + e2e): `Recover(onPanic=mx.Panics.Inc) → DenyCORS → MaxBody(256KiB) → mux`. `DenyCORS` returns `403 FORBIDDEN` for `OPTIONS` with an `Origin` and NEVER emits `Access-Control-*` headers.
- **Sybil/PoW dormancy** (GW-INV-20 family): all M2 Sybil gates default `0`=disabled and short-circuit BEFORE any DB work; `INSTALL_POW_MODE` is a three-state enum `off`/`shadow`/`enforce` (zero-value/empty/any-other-value ≡ off, byte-for-byte unchanged `/install`), PoW challenge is stateless `base64(rand16‖unixTs‖HMAC[:16])` with 120s TTL, difficulty = leading-zero-bits of `SHA256(challenge"."nonce)`, and nonce-once via `httpx.NonceCache` (bounded LRU+TTL). A live `shadow`/`enforce` mode REQUIRES a non-empty env `INSTALL_POW_SECRET` (`CONFIG_POW_SECRET_REQUIRED` fail-fast on both Load and hot-edit).
- These 40 invariants are the per-slice acceptance criteria; each MUST be re-implemented with an equivalent test (the AGENTS.md "红线 → 测试映射" table names the existing guards to port).
